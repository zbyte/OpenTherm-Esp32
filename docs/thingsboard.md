# Параметры платы в ThingsBoard

Плата — источник истины: всё считает и решает она, ThingsBoard только показывает и передаёт
команды. Без связи отопление работает по сохранённым настройкам.

Связь — MQTT, токен устройства как имя пользователя (`mqtts://` на 8883, на 1883 — без TLS).

| Направление | Топик | Что |
|---|---|---|
| плата → сервер | `v1/devices/me/telemetry` | телеметрия |
| плата → сервер | `v1/devices/me/attributes` | клиентские атрибуты |
| сервер → плата | `v1/devices/me/attributes` | изменения общих атрибутов `set_*` |
| плата ↔ сервер | `v1/devices/me/attributes/request/1`, `…/response/+` | запрос всех `set_*` при подключении |
| сервер → плата | `v1/devices/me/rpc/request/+` | RPC-команды; ответ в `…/rpc/response/<id>` |

## Телеметрия

Ключ уходит, когда значение сдвинулось не меньше порога; раз в 10 минут и при подключении —
все ключи целиком. Ключ без достоверного значения (датчик не отвечает, нет связи с котлом)
не отправляется — на сервере остаётся последнее известное.

| Ключ | Тип | Что | Порог |
|---|---|---|---|
| `room` | °C | управляющая температура: датчик или их сочетание по атрибуту `sensor` | 0,2 |
| `target` | °C | цель регулятора, см. ниже | 0,1 |
| `flow_set` | °C | уставка подачи, которую плата отправила котлу | 0,5 |
| `flow` | °C | фактическая температура подачи от котла | 0,5 |
| `modulation` | % | относительная модуляция котла | 5 |
| `state` | строка | `heating` — горелка/ТЭНы включены; `warm` — тепло запрошено, котёл держит температуру; `idle` — запроса нет | — |
| `demand` | bool | плата запрашивает отопление у котла | — |
| `flame` | bool | горелка/ТЭНы включены (только при связи с котлом) | — |
| `ot_ok` | bool | есть связь с котлом по OpenTherm (нет 5 обменов подряд — `false`) | — |
| `boiler_fault` | bool | котёл сообщает об ошибке; без связи всегда `false` | — |
| `boiler_error` | строка | `нет`; или флаги ошибки через запятую и `код котла N`; или `неизвестно: нет связи с котлом` | — |
| `oem_fault` | число | код ошибки котла (OEM), 0 — нет; только при связи | — |
| `faults` | биты | ошибки термостата: 1 — нет управляющего датчика, 4 — ошибка котла или нет связи | — |
| `t1` / `t2` | °C | DS18B20 на разъёмах J2 / J3 | 0,2 |
| `t_board` | °C | BMP180 на плате (завышает из-за нагрева ESP32) | 0,2 |
| `pressure` | гПа | атмосферное давление (BMP180) | 1 |
| `power` | Вт | оценка мощности: модуляция × номинал котла (`BOILER_POWER_W`, 18 кВт); без данных модуляции «ТЭНы включены» = полная мощность | 100 |
| `energy` | кВт·ч | накопленная оценка энергии; переживает перезагрузку, отправляется не чаще раза в минуту | 0,01 |
| `rssi` | дБм | уровень сигнала Wi-Fi | 6 |
| `clock` | строка | местное время платы `ГГГГ-ММ-ДД ЧЧ:ММ:СС` (часовой пояс — атрибут `tz`), `неизвестно` до первой синхронизации; по нему работает расписание | раз в минуту |
| `ntp_age` | мин | сколько минут назад время синхронизировано по NTP (`pool.ntp.org`, раз в час); нет ключа — NTP ещё не ответил ни разу. Больше ~60 — синхронизация не проходит | вместе с `clock` |

Флаги `boiler_error` (OpenTherm ID5): «нужно обслуживание», «блокировка, нужен сброс»,
«низкое давление воды», «ошибка горения/нагрева», «давление воздуха», «перегрев
теплоносителя».

### Что такое `target` и `flow_set`

Режим (`mode`) определяет, что регулирует плата:

| Режим | `target` | `flow_set` |
|---|---|---|
| `home` | `temp_set` — комнатная, °C | PI-регулятор по `room`, 25–75 °C |
| `leave` | 16 °C — комнатная | PI-регулятор по `room`, 25–75 °C |
| `manual` | `boiler_set` — уставка подачи | = `boiler_set`, комната не учитывается |
| `auto` | точка расписания — уставка подачи; 0, если по расписанию котёл выключен | = точке расписания; комната не учитывается |
| `heating = false` (любой режим) | 5 °C — защита от замерзания | PI-регулятор по `room` |

- Точка расписания ниже 20 °C — котёл выключен (`demand = false`; `flow_set` при этом
  показывает минимальные 25 °C, но запроса нет).
- В `auto` и `manual`, если комната остыла ниже 5 °C, котёл включается на 45 °C.
- В `auto`, пока время не получено по NTP, работает `boiler_set`.
- Нет управляющего датчика больше 2 минут (`faults` & 1) в `home`/`leave` — фиксированная
  подача 45 °C.

## Клиентские атрибуты

Отправляются при подключении и при каждом изменении (с панели, веб-страницы, консоли или
кнопкой).

| Ключ | Что | Допустимо |
|---|---|---|
| `heating` | отопление включено; `false` — только защита от замерзания | true / false |
| `mode` | режим, см. таблицу выше | `auto`, `manual`, `home`, `leave` |
| `temp_set` | комнатная уставка для `home`, °C | от `lower` до `upper` |
| `boiler_set` | уставка подачи для `manual` (и для `auto` без времени), °C | 20–80 |
| `lower` / `upper` | границы `temp_set`, °C | 5–15 / 25–35 |
| `sensor` | управляющий датчик: `1` — t1, `2` — t2, `3` — t_board, `4` — пусто; `min` / `avg` — по всем датчикам, кроме BMP180 | `1`–`4`, `min`, `avg` |
| `tz` | часовой пояс, минуты от UTC (Москва — 180) | −720…840 |
| `schedule` | недельное расписание, JSON (см. ниже) | — |
| `sched_mon` … `sched_sun` | то же по дням текстом: `06:00 55; 08:30 40; 17:00 55; 22:30 40` | — |
| `fw` | версия прошивки | — |
| `ip` / `wifi` | IP-адрес и имя сети Wi-Fi | — |
| `reset` | причина последней перезагрузки: `power-on`, `software`, `panic`, `task watchdog`… | — |

### Расписание

`{"mon":[["06:00",55.0],["08:30",40.0],["17:00",55.0],["22:30",40.0]],"tue":[…],…,"sun":[…]}`

7 дней с понедельника × 4 точки «время, уставка подачи °C». Уставка действует с указанного
времени до следующей точки, в том числе через полночь и на следующий день. Ниже 20 °C — котёл
выключен. Расписание действует только в режиме `auto`, по местному времени платы (`tz`).
Повторяющиеся точки означают, что точек меньше четырёх.

## Команды с панели

**Общие (shared) атрибуты** — доходят и до платы, которая была не в сети: при подключении она
запрашивает все `set_*` и применяет те, что отличаются от последних применённых ею. Поэтому
старое значение на сервере не затрёт то, что потом поменяли на самой плате. Результат — в
клиентских атрибутах и в логе платы (`cloud: shared <ключ> applied` / `REJECTED`).

| Ключ | Значение |
|---|---|
| `set_heating` | true / false |
| `set_mode` | `auto` / `manual` / `home` / `leave` |
| `set_temp`, `set_boiler`, `set_lower`, `set_upper` | число, °C |
| `set_sensor` | `1`–`4`, `min`, `avg` |
| `set_tz` | минуты от UTC |
| `set_schedule` | JSON расписания (объект или строка) — его пишет виджет расписания |
| `set_sched_all` | текст одного дня для всех семи дней |
| `set_sched_mon` … `set_sched_sun` | текст одного дня: 1–4 точки `ЧЧ:ММ темп` через `;`, дробная часть через точку |

**RPC** (только пока плата в сети): `setHeating`, `setMode`, `setTemp`, `setBoiler`,
`setLimits` `{"lower":10,"upper":30}`, `setSensor`, `setTz`, `setSchedule` и парные `get*`;
`getState` — все настройки; `cli` `"status"` — команда консоли, в ответе её вывод. Ответ на
одно поле — голое значение, на несколько — объект; ошибка — `{"error":"…"}`.

Неверное значение плата отклоняет и оставляет прежнее; настоящее значение видно в клиентском
атрибуте.

## Обновление прошивки

Через пакеты OTA ThingsBoard («Устройства и активы → OTA updates»).

1. Собрать прошивку с новой версией (`CONFIG_PROJECT_VERSION` в `app_default.config`,
   затем `.\build.ps1 clean` и `.\build.ps1`).
2. Добавить пакет: **Title** `opentherm_esp32s3` (другое название плата не примет),
   **Version** — та же, что `CONFIG_PROJECT_VERSION`, профиль устройства, тип Firmware,
   файл `dist/opentherm_esp32s3_<версия>/opentherm_esp32s3_UG_<версия>.bin`, контрольная
   сумма — по умолчанию (SHA-256).
3. Назначить пакет устройству (карточка устройства → «Assigned firmware») или профилю.

Плата получает общие атрибуты `fw_title`, `fw_version`, `fw_size`, `fw_checksum`,
`fw_checksum_algorithm` и, если версия новее своей, качает образ кусками по 1 КБ
(`v2/fw/request|response`). Обрыв связи не страшен: после переподключения загрузка
продолжается с того же куска. Нет ответа 4 с — кусок запрашивается снова, 8 с — плата сама
переподключается (провайдер может «замораживать» соединение после нескольких килобайт);
10 минут без движения — отказ. Пока идёт загрузка, при переподключении не отправляются
полные атрибуты и телеметрия — только продолжение загрузки. Затем проверка контрольной
суммы и самого образа, перезагрузка; новая прошивка подтверждает себя через 60 с в сети,
иначе (нет связи с ThingsBoard 5 минут или сбой) загрузчик возвращает старую.

| Телеметрия | Что |
|---|---|
| `current_fw_title`, `current_fw_version` | что работает сейчас (при каждом подключении) |
| `fw_state` | `DOWNLOADING` → `DOWNLOADED` → `VERIFIED` → `UPDATING` → после перезагрузки `UPDATED`; или `FAILED` |
| `fw_error` | причина `FAILED`: контрольная сумма, образ не подошёл, загрузка встала, откат |
| `fw_progress` | процент загрузки, каждые 10 % |

Защита платного канала: версия, которая откатилась, больше не скачивается; неудачная
загрузка повторяется не больше 3 раз на версию. Образ ~1,1 МБ — столько и уйдёт трафика.
Состояние на плате: консольная команда `tb` (байты, число переподключений).

Пакет старше работающей прошивки не ставится (версии сравниваются по числам: 1.2.10 > 1.2.9):
прошивка, залитая по сети (`.\build.ps1 ota`), остаётся, пока не назначат более новый пакет.
Вернуться на старую — загрузить её образ в ThingsBoard под большей версией.

Связь с ThingsBoard Cloud через свой брокер Mosquitto — [mosquitto.md](mosquitto.md).
