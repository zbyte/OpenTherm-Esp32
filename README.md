# OpenTherm-термостат на ESP32-S3 с ThingsBoard

Прошивка управляет электрокотлом BAXI Ampera (18 кВт, 6 реле по 3 кВт, бойлер ГВС через
трёхходовой клапан) по OpenTherm. Регулирование, расписание и
защита выполняются **на самом устройстве**; облако [ThingsBoard](https://thingsboard.io)
(MQTT) — только телеметрия, пульт и редактор настроек. Без интернета устройство продолжает
работать по последним настройкам.

- Сборка: фреймворк [TuyaOpen](https://github.com/tuya/TuyaOpen) v1.9 (платформа ESP32, ESP-IDF 5.4)
- Облако: ThingsBoard Cloud (`mqtt.eu.thingsboard.cloud:8883`, TLS), устройство по токену доступа
- Плата: адаптер OpenTherm_ESP32S3 rev 4 (`README.pdf`) с модулем ESP32-S3 SuperMini

## Железо

| | |
|---|---|
| Модуль | ESP32-S3FH4R2: 4 МБ флеш, 2 МБ quad PSRAM, только родной USB (Serial/JTAG) |
| OpenTherm TX / RX | GPIO13 / GPIO12 (адаптер Ihor Melnyk на PC817) |
| DS18B20 №1 / №2 | GPIO10 / GPIO11 (у каждого своя линия, без поиска адресов); китайским клонам нужно **VDD 5 В** (см. ниже) |
| BMP180 (I²C) | SDA GPIO8, SCL GPIO9 — температура платы (завышает) и давление |
| Кнопка | BOOT (GPIO0) |
| Светодиод | WS2812 на GPIO48, порядок байтов GRB |

Пины и полярности меняются в `Kconfig` (раздел «Opentherm ESP32-S3 hardware»).

## Сборка и прошивка

Нужен TuyaOpen в `%USERPROFILE%\TuyaOpen` (или переменная `OPEN_SDK_ROOT`).

```powershell
.\build.ps1                 # сборка
.\build.ps1 clean           # полная очистка — после правки Kconfig, sdkconfig.overlay, app_default.config
.\build.ps1 flash           # сборка + прошивка COM5 (сам переводит чип в загрузчик, 3 попытки)
.\build.ps1 flash-manual    # если автоматически не вышло: BOOT + RESET вручную, потом эта команда, потом RESET
.\build.ps1 log             # лог устройства, 20 с, без перезагрузки (USB)
.\build.ps1 ota [IP]        # сборка + обновление по Wi-Fi (без IP — поиск платы в локальной сети)
.\build.ps1 cmd "status"    # команда консоли на плате по Wi-Fi + свежий лог
.\build.ps1 rlog            # лог платы по Wi-Fi (последние ~12 КБ)
.\build.ps1 webpass         # адрес и пароль веб-интерфейса
```

**Локальный HTTP-сервер платы** (порт 8080), доступен из той же сети:
- `http://<IP платы>:8080/` — веб-интерфейс: состояние, котёл, датчики, энергия и формы
  настроек и расписания; `/log` — лог. Вход: `admin` + пароль из `.\build.ps1 webpass`.
- Обновление по Wi-Fi (`POST /ota`) и консоль (`POST /cli`) — для `build.ps1`, по токену.
- Пароль и токен лежат в `include/ota_secret.h` (создаёт `build.ps1`, в git не попадает).
- Новая прошивка грузится «на проверке» и подтверждает себя через 60 с работы **с
  ThingsBoard на связи**; при сбое, зависании или без связи 5 минут — откат на предыдущую.

Почему не `tos.py flash`: `tyutool` на родном USB обрывает запись. Плата описана прямо в
проекте, SDK не правится:
- `Kconfig` — 4 МБ флеша (`PLATFORM_FLASHSIZE_4M`), консоль на USB-JTAG, пины, пределы регулятора;
- `sdkconfig.overlay` — quad PSRAM, откат прошивки при неудачном OTA, задача MQTT на ядре 0; подмешивается через `SDKCONFIG_DEFAULTS` в `build.ps1`;
- `esp_components/ot_port` — компонент ESP-IDF (TuyaOpen подключает `esp_components/` сам).

## Подключение: Wi-Fi и ThingsBoard

- **ThingsBoard:** создать устройство, скопировать его токен доступа. Значения по умолчанию
  вшиваются из `include/tb_secret.h` (образец `tb_secret.h.example`, файл в `.gitignore`);
  на плате их меняют веб-формой «Подключение» или консолью `tb host <сервер> [порт]`,
  `tb token <токен>` (порт 8883 — TLS, 1883 — без шифрования).
- **Свой брокер** перед ThingsBoard (Mosquitto с мостом, `server/mosquitto/`) — если провайдер
  рвёт связь с ThingsBoard Cloud: [docs/mosquitto.md](docs/mosquitto.md). На плате: `tb host
  <сервер> 1883`, `tb pass <пароль>`.
- **Wi-Fi** — до двух сетей, в KV под ключами `netinfo` и `netinfo2`. Плата подключается к
  той, которую находит: если сеть не видна, через несколько секунд пробует другую, и остаётся
  на подключённой, пока связь не пропадёт. Задать: веб-форма «Подключение» или
  `wifi <сеть> [пароль]`, `wifi2 <сеть> [пароль]` (`wifi2 -` — убрать вторую).
- **Точка настройки:** без сохранённого Wi-Fi или после удержания кнопки 5–10 с плата на
  10 минут поднимает точку доступа `OpenTherm-XXXX` (пароль — пароль веб-интерфейса,
  `.\build.ps1 webpass`). Веб-интерфейс — `http://192.168.4.1:8080/`. На это время
  клиентская связь Wi-Fi отключается (TuyaOpen не умеет обе роли сразу).
- Время — по SNTP (`pool.ntp.org`), часовой пояс — настройка `tz` (минуты от UTC, по
  умолчанию 180).

## Обмен с ThingsBoard

Полное описание всех ключей и логики — [docs/thingsboard.md](docs/thingsboard.md).

Устройство — источник истины. Измерения уходят **телеметрией**, настройки — **клиентскими
атрибутами**. Изменения с панели приходят **RPC-командами** (только пока плата в сети) или
**общими (shared) атрибутами** `set_*` (доходят и после переподключения) и проходят через те же
функции, что веб-интерфейс и консоль. Общий атрибут применяется, только если отличается от
последнего применённого (KV `tb_seen`), поэтому старое значение с сервера не затирает то, что
поменяли на плате. Результат — в логе: `cloud: shared <ключ> applied` или `REJECTED`.

**Телеметрия** (только при изменении больше порога, и всё целиком раз в 10 минут):

| Ключ | Что | Порог |
|---|---|---|
| `room` | управляющая температура, °C | 0,2 |
| `target` | цель регулятора, °C | 0,1 |
| `flow_set` / `flow` | уставка подачи / фактическая подача, °C | 0,5 |
| `modulation` | модуляция котла, % | 5 |
| `state` | `heating` / `warm` / `idle` | — |
| `demand`, `flame` | запрос тепла, ТЭНы | — |
| `ot_ok` | есть связь с котлом по OpenTherm | — |
| `boiler_fault` | котёл сообщает об ошибке (false, если связи нет) | — |
| `boiler_error` | текст: «нет», флаги ошибок OpenTherm (ID5) и код котла, или «неизвестно: нет связи с котлом» | — |
| `faults`, `oem_fault` | биты ошибок термостата (1 — датчик, 4 — котёл/связь), код ошибки котла | — |
| `t1` / `t2` / `t_board` | DS18B20 на J2 / J3, BMP180, °C | 0,2 |
| `pressure` | давление, гПа | 1 |
| `power` / `energy` | оценка мощности, Вт / энергии, кВт·ч (не чаще раза в минуту) | 100 Вт |
| `rssi` | сигнал Wi-Fi, дБм | раз в минуту |
| `ch_active` / `dhw_active` | котёл работает на отопление / греет бойлер ГВС | — |
| `ch_pressure` / `dhw_temp` | давление в системе, бар / температура бойлера, °C | 0,05 / 0,5 |
| `max_power` | ограничение мощности, принятое котлом, кВт | 0,1 |
| `boiler_stalled` | тепло запрошено, подача на 5 °C ниже уставки, а котёл не греет 10 минут | — |
| `ot_timeouts` / `ot_framing` / `ot_parity` / `ot_echo`, `ot_last_bad` | ошибки линии OpenTherm с загрузки и последний испорченный обмен | раз в минуту |

**Атрибуты:** `heating`, `mode` (`auto`/`manual`/`home`/`leave`), `temp_set`, `boiler_set`,
`lower`, `upper`, `sensor` (`1`–`4`/`min`/`avg`), `tz`, `schedule`, `sched_mon`…`sched_sun`
(день текстом: «06:00 55; 08:30 40; …»), а также `fw`, `ip`, `wifi`, `reset`.

**Общие атрибуты** (пишет панель): `set_heating`, `set_mode`, `set_temp`, `set_boiler`,
`set_lower`, `set_upper`, `set_sensor`, `set_tz`, `set_schedule` (JSON, как `schedule`),
`set_sched_all` и `set_sched_mon`…`set_sched_sun` (текст одного дня: 1–4 точки
«ЧЧ:ММ темп» через `;`, дробная часть через точку, недостающие точки повторяют последнюю).
Для котла (не хранятся на плате, применяются при каждом подключении): `set_max_power` (кВт),
`set_dhw` (разрешить греть бойлер), `set_ot_room` (какой датчик отправлять котлу как
комнатную температуру, 0 — никакой). `ot_cmd` — разовые команды котлу (`r 18; w 1 3d00`),
ответ в телеметрии `ot_reply`.

**RPC** (`method` → `params`): `setHeating` true/false, `setMode` "home", `setTemp` 21.5,
`setBoiler` 55, `setLimits` {"lower":10,"upper":30}, `setSensor` "1", `setTz` 180,
`setSchedule` {...}, парные `get*`, `getState` (все настройки) и `cli` "status" — команда
консоли, в ответе её вывод. Ответ на одно поле — голое значение (так ждут виджеты управления
ThingsBoard), на несколько — объект. Проверять удобно виджетом «RPC debug terminal».

**Расписание** (`src/app/schedule.c`): 7 дней с понедельника × 4 точки; температура точки —
уставка подачи котла (30 °C и ниже — котёл выключен) и действует до следующей точки, в том
числе через полночь. В ThingsBoard — объект
`{"mon":[["06:00",55.0],["08:30",40.0],["17:00",55.0],["22:30",40.0]],"tue":[...],...,"sun":[...]}`;
принимается только целиком. Во флеше — 112 байт (7 × 4 × час, минута, температура).

**Виджет расписания** (`thingsboard/`): недельная шкала по дням и редактор, сохраняет
`set_schedule`, ждёт подтверждения платы в `schedule` и предупреждает, если режим не `auto`.
Импорт — в библиотеку виджетов, не в панель: «Ресурсы → Библиотека виджетов → Наборы виджетов →
+ → Импортировать набор виджетов», файл `thingsboard/opentherm_widgets_bundle.json` (набор
«OpenTherm»); или только виджет: «… → Виджеты → + → Импортировать виджет»,
`thingsboard/opentherm_schedule_widget.json`. На панели: добавить виджет «OpenTherm: расписание
котла», источник — устройство, ключи-атрибуты `schedule` и `mode` уже указаны. Исходники —
`thingsboard/schedule_widget/`, JSON собирает `python thingsboard/build_widget.py`.

## Регулирование и защита

Ядро 1: мастер OpenTherm и регулятор (раз в 2 с). Ядро 0: сеть, MQTT, датчики, кнопка,
светодиод, supervisor.

Мастер OpenTherm обменивается с котлом раз в секунду:
- ID0 — статус и включение отопления; бит ГВС по умолчанию выключен (`set_dhw`);
- ID25 — подача; по очереди ID17 модуляция, ID5 ошибки, раз в 20 с ID18 давление и ID26 бойлер;
- ID1 — уставка подачи: при изменении, при включении отопления и раз в минуту, в пределах
  котла (ID49);
- при установлении связи и раз в 10 минут: ID2 — код термостата 4 (без него Ampera
  отклоняет уставку) и ID14 — ограничение мощности;
- раз в 30 с ID24 — комнатная температура выбранного датчика (`set_ot_room`).

Кадр передаёт аппаратный блок RMT (34 символа помещаются в его память), а не программный
цикл: запись во флеш останавливает процессоры, и программный кадр рвался посреди
передачи. Перед перезагрузкой плата дожидается конца кадра на линии.

- Цель: `switch=off` → 5 °C (защита от замерзания); `auto` → расписание, а если время
  неизвестно → `temp_set`; `leave` → 16 °C.
- PI-регулятор → уставка подачи 25–75 °C (`HEAT_FLOW_*` в `Kconfig`, для тёплого пола снизить максимум).
- Нет датчика (нет показаний дольше 2 мин) → фиксированная подача 45 °C, не максимум.
- Нет связи с котлом (5 обменов подряд) или ошибка котла → бит в `fault`.
- Нет Wi-Fi/облака → работа по сохранённым настройкам. По умолчанию (новая плата или
  сброс кнопкой) — режим `home`, 20 °C.
- Watchdog: supervisor кормит аппаратный сторож (10 с) только пока живы задачи котла и
  регулятора; зависание сети плату не перезагружает.
- OTA: новая прошивка подтверждается через 60 с нормальной работы, иначе откат. Обновлять
  можно по Wi-Fi в локальной сети (`.\build.ps1 ota <ip>`) или пакетом OTA из ThingsBoard —
  см. [docs/thingsboard.md](docs/thingsboard.md#обновление-прошивки).

### BAXI Ampera

- В меню котла управление по OpenTherm: «Термостат» → «ZONT Connect» → «использовать»;
  вход внешнего термостата выключен. В этом режиме без термостата котёл стоит на паузе.
- Котёл принимает уставку (ID1) только после кода термостата 4 в ID2.
- **ID14 (максимальная модуляция) — это пункт меню 5.0, ограничение мощности**, в целых
  процентах от 18 кВт с округлением вниз до ступени 3 кВт. После любого обрыва связи или
  перезагрузки платы котёл сбрасывает 5.0 в 0 и перестаёт греть (так же ведёт себя с ZONT,
  [форум BAXI](https://forum.baxi.ru/viewtopic.php?t=9373)). Поэтому плата пишет ID14 при
  каждом установлении связи и раз в 10 минут: `OT_POWER_LIMIT_W` = 15 кВт, процент
  округляется вверх (15 кВт → 84 % → 5 ступеней).
- Бит ГВС в ID0 переводит клапан на бойлер даже при выключенном отоплении.
- Флаг диагностики (0x40 в статусе) горит всегда. Котёл отдаёт ID0, 3, 5, 6, 9, 15, 17, 18,
  25, 26, 48, 49, 56, 57, 127; ID10/11 (параметры котла) и номера 128–255 не поддерживает,
  поэтому 5.0 и 11.0 (насос) через OpenTherm не прочитать. Сброс 11.0 виден только по
  `boiler_stalled`.
- После снятия запроса насос работает ещё некоторое время (выбег) — это котёл.

## Светодиод и кнопка

| Светодиод | Значение |
|---|---|
| сиреневый ровно | кнопка удерживается ≥ 10 с — при отпускании сброс настроек отопления |
| голубой ровно | кнопка удерживается 5–10 с — при отпускании точка настройки на 10 минут |
| красный, 1 Гц | ошибка: датчик, котёл или связь OpenTherm |
| синий, быстро | включена точка настройки |
| жёлтая вспышка раз в 2 с | нет облака (отопление работает) |
| оранжевый | в сети, ТЭНы включены |
| зелёный | в сети |

Кнопка срабатывает **при отпускании** — плата не перезагружается с зажатым GPIO0.

## Консоль (CLI) и стенд без котла

Консоль на COM5: `status`, `heat on|off`, `set 21.5`, `mode auto`, `limits 5 30`,
`sched` / `sched set 1 1 06:30 21.5` / `sched hex`, `time <UTC epoch>`, `sensor`, `sensor pull auto|on|off`,
`ot log on`, `ot raw 0 25 0`, `ot stats` (ошибки линии), `ot dhw on|off`, `ot room <0-4>`,
`ot power <кВт>`, `led` (тест цветов), `wdt stall boiler` (тест watchdog),
`wifi <сеть> [пароль]` / `wifi2 <сеть> [пароль]` / `wifi2 -` / `wifi setup`, `tb` / `tb host <сервер> [порт]` / `tb token <токен>`,
`tb pass <пароль>` (свой брокер, [docs/mosquitto.md](docs/mosquitto.md); `-` — убрать),
`tz 180`, `report` (отправить всё в ThingsBoard заново), `factory`.
Те же команды доступны по сети: `POST /cli` (`.\build.ps1 cmd`) и RPC `cli` из ThingsBoard;
строки с паролем или токеном в лог не пишутся.

**Эмулятор котла** — только на голом модуле, не на плате адаптера (он управляет GPIO12 как
выходом): `sim start bare`, `sim speed 60`, `sim fault 42`, `sim mute on`. Модель: электрокотёл
18 кВт (6 ступеней по 3 кВт) + дом; эмулятор отвечает мастеру по тем же пинам через
внутреннюю петлю GPIO, температура комнаты идёт в датчик №1.

## Известные особенности

- **Клоны DS18B20 не работают от 3,3 В на VDD:** считают себя паразитно запитанными и сбоят
  (нули, линия в нуле, правдоподобные с виду −41 °C). Лечится питанием VDD от 5 В (красный
  провод на +5V, GND и DQ — в клемме: подтяжка DQ остаётся 3,3 В, вывод ESP32 в безопасности).
  Прошивка для паразитного питания подтягивает DQ на время измерения, выбросы отсекает:
  значение дальше 3 °C от текущего принимается после 3 согласованных замеров подряд, остальное —
  медиана по 5 (10 с). `sensor` показывает причины ошибок, тип питания, ROM-код и сырые байты.

- Автоматический переход в загрузчик по USB на этом ПК иногда не срабатывает
  (`Write timeout`) — тогда `flash-manual`. После неудачной попытки USB может «залипнуть»
  до переподключения кабеля; прошивка при этом работает.
- TuyaOpen собирает mbedTLS с `MBEDTLS_THREADING_ALT`, но функции мьютексов сам не
  регистрирует. Без них любой TLS ESP-IDF падает на `mbedtls_ctr_drbg_seed
  returned -0x0034`; прошивка регистрирует их сама (`esp_components/ot_port/net_port.c`).
- Сообщения компонентов ESP-IDF (Wi-Fi, TLS, MQTT) уровня «предупреждение» и выше попадают
  в общий лог, в том числе в `/log`.
- Макросы логов TuyaOpen не проверяют формат: `tal_system_get_millisecond()` 64-битный — приводить явно.
- После смены `CONFIG_PROJECT_VERSION` обязательно `.\build.ps1 clean`: иначе в образ попадает
  старая строка версии, плата после обновления называет себя прежней версией и сообщает в
  ThingsBoard об откате (так случилось с 1.2.19).
